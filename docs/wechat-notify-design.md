# 微信公众号 → EduPlay 大屏投屏 · 设计方案

> 状态：设计稿（未实现）。目标是把「老师在微信里发一句话」变成「教室大屏弹窗 + 语音播报」。
> 已确认前提：公众号为**订阅号**（类型待最终确认）；一个教师账号允许多台设备同时投屏。

## 1. 目标与边界

**目标**

- 老师在微信公众号对话框里发送带 `#` 前缀的文本（如 `#通知 #3班 #今天下午第三节调课到实验室`）。
- 云端识别指令 → 推送到该教师名下的 EduPlay 设备 → 大屏弹窗 + 语音播报。
- 老师关机/断网期间的消息不丢，联网后补推（有有效期）。
- **支持多台设备**（含 U 盘便携版插在不同教室的电脑上使用），可按**教室短名定向投屏**（`#通知 #3班 #…`）。

**不做（首版）**

- 不接收学生名单、成绩等隐私数据到云端；投屏内容只走**纯文本**。
- 不处理图片/语音/视频消息（回执提示"暂只支持文字"）。
- 不做群发、不做家长触达、不做消息已读回执。

---

## 2. 三个身份，一次说清

这是整个设计的骨架。很多复杂度都来自把这三个身份混在一起谈：

| 身份 | 从哪来 | 作用 | 现状 |
|---|---|---|---|
| **教师账号** | EduPlay 云端注册（`/api/v1/auth/local/register`，已有） | "老师是谁" | ✅ 已存在 |
| **微信 openid** | 关注公众号后微信给的，每号唯一 | "哪个微信在发消息" | 新增 |
| **设备 deviceId** | `installationId`（本机生成 UUID，存 `userData/device.json`，见 §7.1） | "投给哪块屏" | 新增 |

关系与数据流向：

```
openid ──(配对码确认)──▶ 教师账号 ──(1 : N)──▶ 设备A / 设备B / 设备C
                           │
             消息路由：openid → 教师账号 → N 台"启用接收"的设备
```

两个直接结论：

1. **绑定是在「教师账号」层面，不是在设备层面。** 老师只要在任意一台设备上完成一次配对，**所有设备**的投屏就都通了，不需要每台单独绑。
2. **设备不需要"证明自己是谁"**，它只持有本机的云端 token + 自己的 `deviceId`。设备不能被"绑定到某个微信"——微信消息从来不会定向到设备本身，定向靠的是**短名（tag）**这个路由键（§7.2）。

## 3. 订阅号的能力边界（决定方案形态，必须先看）

你设想的「注册 → 登录确认 → 发投屏消息」里，**"登录确认"这一步在订阅号上不能用微信授权做**。经核实，各账号类型的接口权限如下：

| 接口 | 未认证订阅号 | 认证订阅号 | 认证服务号 | 本项目 |
|---|---|---|---|---|
| 接收消息 / **被动回复** | ✅ | ✅ | ✅ | **✅ 核心依赖** |
| 自定义菜单 | ✅ | ✅ | ✅ | 可选，方便老师找到入口 |
| 客服消息（主动推送） | ❌ | ✅ | ✅ | ❌ 不需要 |
| **网页授权（OAuth 登录页）** | ❌ | ❌ | ✅ | ❌ **订阅号拿不到** |
| 生成带参数二维码（扫码绑定） | ❌ | ✅ | ✅ | ❌ 不需要 |
| 模板消息 / 群发 | ❌ | ✅ | ✅ | ❌ 不需要 |

> 多个来源一致确认：**订阅号（无论是否认证）都不支持网页授权**，只有已认证的服务号支持；未认证订阅号也拿不到带参数二维码。

**怎么确认自己是哪种号**：登录 `mp.weixin.qq.com` → 右上角账号名旁会标 `订阅号` / `服务号`；再看 **设置与开发 → 接口权限 → 网页服务**，若没有「网页授权」或显示"未获得"，就说明走不了 OAuth。测试号（`mp.weixin.qq.com/debug/cgi-bin/sandbox`）**权限等同于已认证服务号**，所以开发阶段能拿它验证 OAuth，但那只验证接口、**不能用来验证我们的正式流程**。

**这个约束带来的唯一影响**：绑定必须用**配对码**，不能用扫码/授权登录。这不是降级——见下节。

## 4. 绑定机制：双向配对码（等价于"登录确认"）

### 4.1 为什么配对码就是"证明是同一个老师"

你要的语义是「证明平台上的用户和这个微信用户是同一个老师」。微信授权页只是达成它的一种手段，而**配对码在语义上更严格**——它要求操作者**同时持有**两边的凭据：

```
持有 EduPlay 教师账号（已登录）  +  持有该微信号（能发出消息）  ⇒  确认是同一人
```

这是一个**双因素持有证明**：光有老师账号不行（拿不到微信侧），光有那个微信号也不行（进不了 EduPlay）。而微信授权页反而更弱——它只证明"这个微信登录过"，**不证明"这个微信属于当前登录的教师账号"**，所以即便是服务号，也还得再做一次账号关联。配对码一步到位。

### 4.2 两个发起方向都要有

老师的心智不一定从 EduPlay 出发——很可能第一反应是打开微信。所以两个方向都支持，落到同一条绑定记录：

**方向 A｜EduPlay 发起（推荐主路径）**

```
1. EduPlay「设置 → 微信投屏」点「绑定微信」
   本地 backend → 云端 POST /api/v1/wechat/binding-code  → 得到 482913（5 分钟有效）
2. 界面显示：请在公众号发送  #绑定 482913
3. 老师发送 → 云端校验 → 建立 binding → 被动回复「✅ 绑定成功（张老师）」
```

**方向 B｜微信发起**

```
1. 老师在公众号发送 #登录
2. 云端生成 736251（5 分钟有效，绑定该 openid）→ 被动回复
   「请在 EduPlay 的「微信投屏」页面输入配对码：736251」
3. 老师在 EduPlay 输入 → 云端确认 → 建立 binding
```

**安全设计**（配对码是可被暴力枚举的，必须处理）：

- 6 位码 + **5 分钟 TTL** + **一次性**（用后即废）。
- **试错上限**：每个码最多 5 次失败即作废；每个 openid 每分钟最多 3 次 `#绑定` 尝试。
  → 攻击者成功率 ≤ 5×10⁻⁶，且限流下不可能在 5 分钟内穷举。
- 同一时间同一教师只保留**最新的 1 个有效码**，生成新码即作废旧码。
- 一个 openid 只能绑一个教师账号（重复绑需先解绑）；一个教师账号可绑多个 openid（老师的两个微信号、年级组长协助）。

### 4.3 生命周期

| 事件 | 处理 |
|---|---|
| 收到 `unsubscribe`（取关） | **自动解绑**（防止微信号换人后仍能投屏） |
| 老师发 `#解绑` | 解绑，被动回复确认 |
| EduPlay 里点「解除绑定」 | 解绑，云端同时清理该账号的在线会话 |
| 运维兜底 | `admin-frontend` 后台可查看并手工解绑 |

## 5. 指令语法

### 5.1 主格式：三段式（用 `#` 分段）

用 `#` 把消息切成三段，**顺序固定**：

| 段 | 语义 | 取值 |
|---|---|---|
| 第 1 个 `#` | **指令类型** | `通知`（普通）｜`紧急`（强投） |
| 第 2 个 `#` | **目标短名** | 已注册短名，或保留值 `全部` |
| 第 3 个 `#` 起 | **正文** | 原样透传，**不做任何解析** |

**换行只是排版，不是语法。** 下面两种写法完全等价：

写法 A —— 单行（**PC 微信推荐**）
```
#通知 #3班 #请王小明同学到办公室
```

写法 B —— 多行（**手机微信推荐**）
```
#通知
#3班
#请王小明同学到办公室
```

⚠️ **PC 微信里回车是「发送」，换行要按 `Shift + Enter`。** 老师若习惯性按回车，只会发出第一行 `#通知`。所以 PC 端推荐单行写法。两种都能解析，老师不必记哪个。

### 5.2 解析实现：一条正则同时吃下单行与多行

```java
Pattern P = Pattern.compile("^#(通知|紧急)\\s+#([^\\s#]+)\\s+#([\\s\\S]*)$");
```

关键点：`\s` **同时匹配空格与换行** ⇒ 单行、多行、多空行、全角空格的排布都由同一条正则覆盖，**不需要为两种写法写两套逻辑**。

字段语义由 `#` 的**出现顺序**决定，而不是由行号决定。这个选择带来一个重要的容错性质：**正文里再出现 `#` 不会破坏解析**，因为正则只把**前两个** `#` 当分隔符。

```
#通知 #3班 #小明这次考了#1名    → 正文 = "小明这次考了#1名"
```

### 5.3 边界情况（每一条都必须显式处理）

| 情况 | 处理 | 理由 |
|---|---|---|
| 第 2 段没命中任何短名（老师打错字，或把正文写在了这里） | 回执**报错 + 列出可用短名**；**不投屏、不回退成全推** | ⚠️ 若采用"没命中就当正文"，则**打错短名会变成全校广播**——代价远大于让老师多看一眼回执 |
| 只收到 `#通知` 一行（PC 微信按了回车） | 回执教会完整格式（含单行写法示例） | 静默失败会让老师以为系统坏了 |
| 正文为空 | 报错「缺少正文」 | |
| 正文 > 500 字 | 截断 + 回执提示 | |

**报错回执长这样**（既是报错，也是教学）：

```
未找到短名「明天停课」。
要全推请写：#通知 #全部 #正文
发送 #状态 查看可用短名
```

### 5.4 单字段指令（无正文，保持原样）

```
#绑定 482913     方向 A 配对
#登录            方向 B 配对（发起）
#解绑
#状态            绑定状态 + 设备列表（名称/短名/在线/接收开关）
#帮助            指令说明
```

**解析顺序固定**：先试三段式（`通知` / `紧急` 开头）→ 再试单字段指令 → 都不匹配则回复可用指令列表。顺序固定是为了避免 `#通知…` 被单字段规则误吃。

### 5.5 全局策略

**默认只处理带已知前缀的消息**（`#通知` / `#紧急` / `#绑定` / `#状态` / `#帮助` / `#登录` / `#解绑`），其余**不入库、不投屏**。

这条是刻意的。如果"所有消息都投屏"，老师手滑转发的内容也会上大屏，误触发概率极高。前缀要求的作用是**把「微信聊天」和「控制指令」两个语义分开**。

- 兼容全角 `＃`（统一转半角后再解析）。
- 未识别前缀 → 被动回复可用指令列表（对新关注者友好）。
- 未绑定的 openid → 回执引导：「请先在 EduPlay 中获取配对码，然后发送 #绑定 你的配对码」。
- **不做"无前缀默认投屏"开关**——它会把这个安全边界废掉，收益不值。

## 6. 投屏策略：三类行为，全部可配

你说的全屏、气泡、播报、免打扰都做，但要**按消息优先级分层**，否则「下课了」和「紧急疏散」用同一种表现就是设计失败。

### 6.1 策略矩阵

| 优先级 | 触发 | 视觉 | 播报 | 关闭方式 | 绕过免打扰 |
|---|---|---|---|---|---|
| `NORMAL` | `#通知` | 角落气泡（右下，不抢焦点） | 只播提示音 | 默认 12s 自动消失 | ❌ |
| `URGENT` | `#紧急` | 全屏强投（置于最上层） | **TTS 朗读正文** | 手动点击 / Esc | ✅ 默认绕过 |
| `SILENT` | 免打扰时段内的 `NORMAL` | 不投屏，**只写历史** | 无 | — | — |

⚠️ `SILENT` 刻意**仍然落本地历史**：这样老师能事后回看"刚才午休来了什么"，而不是彻底丢失。完全不记会让老师以为系统坏了。

### 6.2 气泡的技术形态（和全屏是两种窗口）

角落气泡**不是一个小号全屏窗口**，它需要不同的窗口属性：

- 无边框、透明背景、`focusable: false`（**不能抢焦点**——老师正在讲课，气泡夺走键盘焦点会打断演示）、`skipTaskbar: true`、`resizable: false`。
- 用 `screen.getPrimaryDisplay().workArea` 算右下角坐标（用 `workArea` 而非 `bounds`，避开任务栏）。
- 多个气泡同时到达 → **纵向堆叠**（最多 3 个，超出则合并为「还有 N 条通知」），不要互相覆盖。

### 6.3 全屏强投的细节

- 独立 `BrowserWindow`，`fullscreen`、`frame: false`、`skipTaskbar: true`。
- `alwaysOnTop` 必须用 `setAlwaysOnTop(true, "screen-saver")` —— 默认层级压不过某些全屏应用（PPT 放映、播放器）。
- 内容页用**静态本地 HTML**（`loadFile`），不复用 SPA：主窗口关掉、后端没起来时也能投屏。
- 大屏常是**第二块屏**（投影仪/电视）：`screen.getAllDisplays()` 选定显示器再 `setBounds()`；外接屏拔出时回退主屏。⚠️ 要监听 `display-removed` 事件，否则窗口会跑到不存在的坐标上（现象是"投屏了但屏幕上什么都没有"）。
- 新通知到达时**替换**上一条，不堆叠多个全屏窗口。

### 6.4 播报

优先 **Windows 原生 SAPI**（`System.Speech.Synthesis`，中文语音系统自带）——**零依赖、可离线**，与便携版定位一致。在线方案（edge-tts）音质更好但**破坏离线特性**，作为设置项由用户选。

⚠️ 实现注意（项目已踩过的坑）：

- 用 `child_process.spawn` 直接起 `powershell.exe`，**不要用 `Start-Process`**（本机环境块存在仅大小写不同的重复键，会抛异常）。
- 中文文本**不要走命令行参数**：写进 UTF-8 临时文件，脚本用 `[System.IO.File]::ReadAllText($p, [Text.Encoding]::UTF8)` 读，彻底避开编码转手。
- 新通知播报前先 kill 上一条 TTS 进程，避免排队念旧消息。

### 6.5 配置项（**每台设备独立**）

| 配置 | 值 | 存哪 |
|---|---|---|
| 投屏模式 | 跟随优先级 / 强制气泡 / 强制全屏 | 本地 |
| 播报 | 关 / 只提示音 / 朗读正文；音色、语速、音量 | 本地 |
| 气泡停留时长 | 5 / 12 / 30 秒 | 本地 |
| 免打扰时段 | 可多段（如 12:00–13:30、22:00–07:00），`#紧急` 是否绕过 | 本地 |
| 显示器 | 主屏 / 指定显示器 | 本地 |
| 设备名 | "教室大屏"、"办公室电脑"（默认 `os.hostname()`） | **云端**（跨设备可见，路由要用） |
| 接收通知 | 开 / 关 | **云端**（路由要用） |

**为什么免打扰放本地**：它是"这台机器现在要不要出声"的本机行为；放云端反而要处理"云端以谁的时区为准"这类烂问题。

## 7. 多设备模型

### 7.1 设备身份：单层，`deviceId` 就够了

> **决策（2026-09-19 修订）**：**不做机器指纹（`hostId`）那层。**
> 曾设计过 `deviceId = installationId@hostId` 的两层方案，复盘后判定为**过度设计**——它想解决的场景在物理上不可能发生。理由见下。

| 值 | 定义 | 存在哪 |
|---|---|---|
| `deviceId` = `installationId`（UUID v4） | 这份安装的持久标识 | `userData/device.json`（**便携版 ⇒ 在 U 盘**） |

- **安装版**：每台机器各自安装 ⇒ `deviceId` 天然不同 ⇒ 天然可区分、可定向。
- **便携版（一人一盘、插哪投哪）**：`deviceId` 跟着 U 盘走，云端视为**同一个终端**。

#### 为什么"同一个 deviceId 跨机器"不是缺陷

判定它是否算缺陷，要看**设备语义的载体是什么**：

| 形态 | 设备指的是什么 | `deviceId` 是否天然正确 |
|---|---|---|
| 安装版 | 一台固定的电脑 | ✅ |
| 便携版（一人一盘、插哪投哪） | **老师的一个可移动终端** | ✅ 也正确 |

第二种语义下，"人走屏走"是**预期行为**而不是异常——设备本来就该跟着老师移动。（反过来说，只有"每间教室固定一台设备、U 盘不挪窝"的用法才会需要区分，而那种用法下每台机器本来就各自安装、`deviceId` 天然不同，仍然不需要 `hostId`。）

更关键的一条硬约束：

> **U 盘是物理实体，同一时刻只能插在一台电脑上。**
> 所以"同一份数据在两台机器上并发投屏"这个**必须靠区分才能避免**的问题，物理上不可能发生。

于是 `hostId` 层剩下的唯一收益，是避免"历史串台"——周一插教室 A、周二插教室 B，两次的 `name`/`tag` 混在一条云端记录里。

⚠️ **2026-09-19 修正后，这个风险的权重上升了**：便携版会登录云端（见下），所以它**一定会**进设备列表、**一定会**跨教室移动；
而 `tag` 指错教室会导致**路由错误**（不只是显示名混）。§7.5 记录了触发条件与轻量解——**仍然不必回到 `hostId` 作为设备键**。

首次连接云端：`POST /api/v1/devices/register {deviceId, name, tag}`（带本机云端 token），云端 upsert。

**设备归属随登录账号走**：同一台电脑换了老师登录，云端把 `device.user_id` 改成新账号，原账号的微信通知不再投到这台。这是合理默认，无需额外确认流程。

#### 便携版与云端的关系（2026-09-19 修正）

> ⚠️ **修正一个错误推断**：曾以为"便携版 `userData` 是全新的（在 U 盘上）⇒ `localStorage` 为空 ⇒ 没有云端 token ⇒ 投屏功能自然沉默"。
> **这个推断是错的。** 老师用便携版照样会**登录云端账号**（游戏商城、云端资源都需要），
> 登录后 token 就落在 U 盘的 `localStorage` 里 ⇒ WS 照常建立、设备照常出现在列表里。

| 项 | 做法 |
|---|---|
| 首启引导 | ❌ 不做。便携版不**专门**引导配投屏，宣传材料也不提 |
| 代码 | ❌ **不加任何 `if (portable)` 分支**（理由见 §7.5） |
| 实际效果 | 老师登录云端后，便携版**就是一台正常设备**：能收投屏、能被定向、出现在设备列表里 |

**这一点反而让"不分形态"的结论更站得住**：便携版不是特例，只是设备语义为"老师的可移动终端"。
它既没有"默认不具备"，也不需要"禁用代码"——因为压根没有什么需要禁用的东西。

### 7.2 路由：从"全部"到"这一块屏"

老师的真实场景是「**叫 3 班的同学去办公室**」——这条只该弹在 3 班，不该全校广播。所以定向不是二期优化项，是**核心能力**。

| 写法 | 目标集合 | 老师的心智 |
|---|---|---|
| `#通知 #全部 #正文` | 该教师所有「接收 = 开」且**在线**的设备 | "哪块屏在就弹" |
| `#通知 #3班 #正文` | **短名 = 3班** 的设备 | "只通知 3 班" |

⚠️ **没有"省略目标"的写法**：第 2 段是必填的目标位。老师想全推时必须显式写 `#全部`。这是 §5.3 那条规则的直接后果——**宁可让老师多打三个字，也不接受"短名打错变成全校广播"**。

#### 为什么用「短名」而不是设备名做路由键

设备显示名为了可读会很长（"八年级3班教室大屏"），让老师在微信里每次敲一遍不现实。所以设备有两个名字：

| 字段 | 例 | 用途 |
|---|---|---|
| `name` | 八年级3班教室大屏 | 给人看的（设备列表、投屏窗口角标） |
| `tag`（短名） | `3班` | **给指令用的路由键**，2–4 字 |

**短名由老师在 EduPlay 设备列表页手填**（已定，不走班级下拉）。

| 手填约束 | 原因 |
|---|---|
| 2–4 字 | 太短易撞、太长打不动 |
| 不含空格、不含 `#` | 会破坏 §5.2 的三段式解析 |
| 建议只用中文 / 数字 / 字母 | 避免全角符号与表情 |
| **`全部` 是保留值** | 不能被任何设备占用，需在保存时校验 |
| 该账号内**允许重复** | 见下 |

⚠️ **`tag` 允许重复** —— 重复即"分组"：把 3 班教室屏和 3 班走廊屏都设为 `3班`，一条指令两块屏同时弹。这样**不需要引入"投屏组"这个独立实体**，一个字段就够。

匹配规则：**精确匹配**（已定）；无匹配时**不投屏**，回执报错并列出可用短名（`#状态` 可随时查全部短名）。**刻意不做模糊/包含匹配**——"3班"误命中 "13班" 在课堂场景里代价太高，不如让老师看一眼列表再发。

#### 接收开关仍然保留

| 操作 | 说明 |
|---|---|
| 单台开关 | 关掉某台不接收（如家里电脑） |
| 批量 | 「**仅保留这台接收**」一键操作 |

刻意**不引入"主设备"概念**：它与接收开关表达同一件事，多一个概念就多一层要解释的规则。

> 另一种做法是引入独立的「投屏点（venue）」实体，`device.venue_id`，一个 venue 可被多台设备承载。它比 `tag` 更灵活（改名不动设备、一台设备可在多个位置间切换）。**首版不做**——`tag` 已覆盖"按教室定向"的主场景；等出现"一台设备频繁在多位置间切换"的真实需求再升级，届时 `tag` 可以直接迁移成 venue 名（见 §7.5）。

### 7.3 ⭐ 多设备让投递状态从"一个值"变成"一张表"

这是多设备引入的**唯一实质性架构变更**，必须在写代码前定好，否则后期要迁移：

```
旧（单设备思路）：notification.status = PENDING | DELIVERED | EXPIRED
新（多设备）：    notification              ← 消息本身（user_id, priority, content, expire_at）
                 notification_delivery     ← 每台目标设备一行（notification_id, device_id, status, delivered_at, attempts）
```

流程：

1. 消息解析成功 → 落 `notification`（`expire_at = now + 24h`）。
2. 解析目标设备集合 → 为每台设备生成一条 `notification_delivery(PENDING)`。**在线设备立即推，离线设备留着**。
3. 设备连上 WS 时，云端 flush 该 **device** 的 `PENDING`（按时间正序，**限 20 条**）。
4. 设备 ack → 该 delivery 置 `DELIVERED`。**每台设备独立 ack，不合并**（否则会误判"都收到了"）。
5. 超过 `expire_at` 仍未投递 → 置 `EXPIRED`，**不补推**。

⚠️ **24 小时过期不是可选项**：某台设备离线一周后上线，会一次性收到所有积压通知，老师会被连续轰炸十几条。这个体验比丢消息更糟。同理，`#状态` 应回报「已投送 2/3 台」。

### 7.4 设备管理页（EduPlay 设置内）

| 能力 | 说明 |
|---|---|
| 设备列表 | 名称、**短名**、在线状态、最后在线时间、接收开关；本机标「本机」 |
| 改名 | 改云端 `name`（显示用）与 `tag`（短名，路由用）；短名做**手填校验**（2–4 字、无空格无 `#`、不占用保留值 `全部`） |
| 接收开关 | 单个切换 + 「仅保留这台接收」 |
| 移除设备 | 删除云端记录并断开其 WS |
| 本机配置 | 显示器、播报、免打扰（见 §6.5） |

**移除设备的语义要明确**：删记录后，那台设备**下次启动会作为"新设备"重新出现在列表里**（因为它的 `deviceId` 还在、token 还有效）。刻意**不做黑名单**——否则 U 盘换电脑、重装系统后会出现"设备再也连不上、老师也不知道为什么"的死锁。代价是：想永久踢掉某台设备，要么关掉它的接收开关，要么让它退出登录。

### 7.5 ⭐ 部署形态与代码分支：不分形态

老师端有两种部署形态（NSIS 安装版 / U 盘便携版）。**代码不为形态做任何分支**，本节记录理由与将来的触发条件。

#### 判定维度应该是"有没有云端会话"，不是"是不是便携版"

| 候选分支条件 | 评价 |
|---|---|
| `if (isPortable)` | ❌ 把投屏开关挂到**部署路径判定**上，而投屏的真实前置条件与之无关 |
| `if (hasCloudSession)` | ✅ **就是现有逻辑**，无需新增判据 |

投屏能跑起来的充要条件是渲染进程通过 `notify:setCloudSession` 交出了 `baseUrl + token`。而这个 token 只在老师**主动登录云端账号**后才在 `localStorage` 出现——**便携版同样会登录云端（游戏商城等都需要）**，所以两种形态下这是**同一个条件**，不存在"便携版天然不成立"。

#### 为什么不分形态

| 理由 | 说明 |
|---|---|
| **① 分支点选错维度** | 按"形态"分支＝用一个新引入的**部署态**判断，替换掉一个已有的**运行态**判断。后者本来就在代码里（登录才有 token），前者还要新写 |
| **② 便携版不是特例** | 它同样登录云端、同样建 WS、同样出现在设备列表里。**没有"特例"要处理，也就没有分支可写**（原写的是"便携版天然沉默"，已修正——那是错的） |
| **③ 编译期分支不可测** | 一旦写下 `if (portable)`，**便携版那条路径在开发机上永远跑不到**（除非真去做一次便携版构建）。两条不可测的分叉，半年后没人敢改 |
| **④ 拦不住、也不该拦** | 老师若主动在便携版里登录了云端账号，投屏会投到 **U 盘当前所在的屏幕**——"人在哪、屏在哪"，行为完全合理。禁止它反而要新增 UI 隐藏逻辑，还得向老师解释一个本不存在的限制 |

#### 什么时候才需要重新考虑

⚠️ **2026-09-19 修正后，这个风险的概率上升了**：便携版既然一定会登录云端、一定出现在设备列表里，
那"老师背着 U 盘在不同教室之间移动"就会真实发生——而**短名（`tag`）也跟着 U 盘走**。

后果比"显示名混了"更实际，是**会指错教室**：

> 老师周一在 3 班把短名设为 `3班`，周二在 4 班电脑上用同一个 U 盘，
> 发 `#通知 #3班 #…` ⇒ 消息投到**他手上这台（此刻在 4 班的）**设备上。

即 **`tag` 的语义是"哪间教室"，而它跟着 U 盘走**，两者在便携版上天然冲突。

| 场景 | 是否需要处理 |
|---|---|
| 一人一盘、**在固定教室**用（校机室常见形态） | ❌ 不需要——短名一直是对的 |
| 一盘**在多间教室轮着插** | ⚠️ 需要，见下 |

**触发条件（真出现抱怨再动，且不必回到 `hostId` 作为设备键）**：
老师反馈「我在 3 班叫它『3班』，插到 4 班还是『3班』，结果通知投错了屏」。

那时的**轻量解**：`device.json` 增一张 `hostTags: { "<hostId>": { name, tag } }`；
插到一台没见过的机器时提示一次「这台是哪间教室？」，然后**把云端 `device.tag` 改成该位置的短名**。
约半小时工作量，不触碰任何已有数据结构。

若需求进一步升级为"同一台设备频繁在多位置间切换、且**每个位置各自独立路由**"（"我只想投给 3 班那块屏，
而不是投给我手上这台"），才考虑 §7.2 提到的 `venue` 实体——那时也**仍然不需要 `hostId` 作为设备键**。

#### 由此产生的约定

- `deviceId` **只由 main 进程生成与持有**，渲染进程不感知。存 `userData/device.json`，首次启动生成，之后不变。
- **不做**机器指纹探测、**不做**注册表读取、**不做**位置认领交互。

## 8. 链路总览与关键协议约束

```
①老师微信 ──▶ ②微信服务器 ──POST──▶ ③admin-backend 回调
                                     验签 → 解析 → 幂等 → 落库
                                     └─▶ 立即返回被动回复 XML（5s 内）
                                          ↓ 异步线程
                                     openid → 教师账号 →（有 @短名 则定向）目标设备集合
                                          ↓ 出站 WebSocket 长连接（教师端主动连出来）
                                     ④Electron main ──▶ ⑤全屏/气泡窗口 + SAPI 播报
                                          └─▶ ack 回云端（每设备独立）
```

**为什么必须"教师端主动出站"**：微信是**服务器主动推**给你（回调 URL 必须公网可达），而教师电脑在校园内网、没有公网 IP，外面连不进来。所以**绝不能让云端去连教师端**——只能让教师端出站建立长连接，借这条已存在的连接反向收消息。出站连接天然穿透 NAT 和出口防火墙，学校侧零配置。

`frp` / `ngrok` 把教师端 7070 映射到公网**只能用于开发调试**：每台机器一个映射（O(N) 管理成本）、校园网常封端口、本地后端整个暴露到公网、老师关机就断。

**5 秒应答 + 幂等（踩了很痛）**

- 回调里**绝不能同步等设备返回**。顺序：验签 → 解析 → 幂等检查 → **落库（快）→ 立即返回被动回复** → 异步再推送。
- 微信超时/失败会**重试最多 3 次**。`MsgId` 建**唯一索引**，插入冲突即视为重复，直接返回 `success` 空串，不重复投屏。
  ⚠️ 幂等必须靠唯一索引，**不要用"先查后插"**——并发重试下会双写。
- **被动回复带投递结果**（2026-09-19 修订）：推送是异步的，但**回执不必含糊**。回执线程用 `CompletableFuture` 等该次通知的 ack，**上限 3s**：
  - 拿到 ⇒ 回「已投屏：八年级3班教室大屏」
  - 无在线设备 / 超时 ⇒ 回「已收到，1 台离线，开机后补推」
  - ⚠️ **为什么要等**：老师最需要知道的恰恰是「屏幕上到底弹出来没有」。设备离线是本功能**最主要的失败模式**，含糊的「已收到」会让他误以为成功。
  - ⚠️ **为什么是 3s 不是 5s**：微信硬限 5s，留 2s 给网络往返与序列化；正常宽带下 ack 在 500ms 内。
  - **超时不回滚**：微信若因超时重试，会被 `MsgId` 唯一索引拦掉并返回 `success` 空串，**不会重复投屏**。
  - 仍未连接设备的情况仍可随时用 `#状态` 查询。
- 未认证订阅号**没有客服接口** ⇒ 无法在异步推送后补发结果 ⇒ 回执只能走被动回复或 `#状态` 查询。这条约束与"不做主动推送"的决策是一致的。

## 11. 那条到云端的连接由谁持有（仍未定，倾向 A）

两个约束合起来会卡住最直觉的做法：

- 老师的云端 token 存在**渲染进程 localStorage**（`StorePage.tsx` 的 `eduplay.cloud.token`），**Electron main 进程读不到**；
- 老师端所有云端调用都**经本地 backend 的 `/cloud-api` 代理**（`CloudApiProxyController`），云端地址存在 `backend` 的 `cloud.base-url` 设置里。

| | 方案 A：main 直连云端 | 方案 B：本地 backend 持有 |
|---|---|---|
| 链路 | 云端 ⇄ main | 云端 ⇄ 7070 ⇄ main |
| token 来源 | 渲染进程经 IPC 交给 main（已在 localStorage） | 渲染进程 POST 给本地 backend |
| 断线重连 | main 里写 JS | Java `HttpClient.WebSocket`（更易测） |
| 通知历史 | 需 main 落 JSON 或 POST 给本地 backend | **直接落 H2** |
| 失败点 | 2 跳 | 3 跳 |

**建议 MVP 走 A**：投屏窗口无论如何只能在 main 里创建，main 已经是必经节点；渲染进程通过 `notify:setCloudSession` 把 `baseUrl + token` 交过去即可（`deviceId` 由 main 首启生成并自持，不依赖任何机器指纹）。需要可靠历史时**过渡做法**是 main 收到后顺手 POST 给本地 backend 存档，将来切 B 无数据断层——**WS 协议与云端接口完全不用改**。

依赖策略（**零新增依赖**）：微信侧手写 SHA1 验签 + 明文模式 + 被动回复（不引 WxJava，Spring Boot 4 / jakarta 兼容性没把握）；main 侧用 **Node 22 的全局 `WebSocket`**（`desktop/` 是 Electron ^36 ⇒ Node 22，已确认）。

## 12. 部署：云端要加 Nginx

微信只允许回调使用 **80 / 443**，而 `admin-backend` 跑在 17070：

```nginx
server {
    listen 443 ssl;
    server_name api.yourdomain.com;
    ssl_certificate     /etc/nginx/ssl/fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/privkey.pem;

    location /api/v1/wechat/ {
        proxy_pass http://127.0.0.1:17070;
        proxy_set_header X-Real-IP $remote_addr;   # 用于可选的 IP 白名单
    }

    location /api/v1/ws/ {                          # WS：Upgrade 头必须透传
        proxy_pass http://127.0.0.1:17070;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 3600s;                   # 默认 60s 会周期性掐断长连接
    }

    location /api/ { proxy_pass http://127.0.0.1:17070; }
}
```

⚠️ 三个常见坑：WS 不透传 `Upgrade` 会握手 400（现象像"后端没响应"）；`proxy_read_timeout` 默认 60s（现象是"每分钟断一次又重连"）；**证书 90 天必须自动续期**（过期后表现为"突然收不到消息也不报错"，极难排查）。

### 12.1 容量画像：为什么长连接不等于"需要很强的服务器"

**先纠正一个直觉**：本方案**不是**教师端反复发请求。它是**一次 HTTP GET 握手**（带 `Upgrade: websocket`）→ 服务端回 `101 Switching Protocols` → **此后这条 TCP 连接上不再有任何 HTTP 请求**，只剩裸字节流；心跳是 WebSocket 帧，不是 HTTP 请求。

对比两种做法在 10,000 台设备下的差别：

| | 轮询（每 5s 问一次） | **长连接（本方案）** |
|---|---|---|
| 每秒请求数 | 10,000 ÷ 5 = **2,000 req/s** | **0**（连接已建立） |
| 每秒帧数 | — | 333（30s 心跳，ping + pong） |
| 每单位开销 | 完整 HTTP 头 + 鉴权 + 可能查库 | 帧约几十字节，**无头、不鉴权、不查库** |
| 结论 | 确实需要集群 + 缓存 | **单台 4C8G 足够** |

**10,000 台设备的资源画像**

| 指标 | 量级 | 说明 |
|---|---|---|
| 并发连接 | 10,000 | Tomcat NIO 下**不占线程**（1 个 IO 线程管数千连接） |
| 堆内存 | 约 0.5–1 GB | 每连接约 30–80 KB（socket 缓冲 + `WebSocketSession` 对象） |
| 心跳带宽 | ~17 KB/s | 30s 一次、每帧几十字节 ⇒ 可忽略 |
| 消息推送 | 每秒个位数 | 每位老师一天几条通知 |
| CPU | 接近空闲 | 瓶颈不在算力 |

⚠️ **一个必须记住的对照**：如果按「1 连接 = 1 线程」的阻塞模型做，10,000 连接 = **10,000 个线程**
（每个栈 0.5–1 MB ⇒ 5–10 GB，且线程切换把 CPU 吃光）。**Tomcat NIO 不会这样**——这是长连接方案能成立的前提。

**真正会先撞上的三面墙**（都不是 CPU）：

1. **文件描述符上限**。Linux `ulimit -n` 默认常是 1024 ⇒ 连到 1000 多就 `Too many open files`。
   上量前必须调 `/etc/security/limits.conf`（`nofile`）、`fs.file-max`、`net.core.somaxconn`、
   `net.ipv4.tcp_max_syn_backlog`，并同步调 Nginx 的 `worker_connections`。**这是 10k 连接第一个撞到的墙。**
2. **`deviceId → session` 的内存 Map 是单点**（见 §11）。一旦部署**第二个实例**，老师可能连在 A
   而微信回调落到 B ⇒ **投递静默丢失**。两条出路：
   - **保持单实例**（10k 量级单机确实够）——`admin-backend` 本来也只有一个；
   - 或引入 **Redis Pub/Sub**：投递时 publish，各实例收到后自查"这设备在我这吗"。广播成本是 O(实例数)，不是 O(连接数)。
   ⚠️ 不要用 Nginx `ip_hash` 来"粘"——同一老师的多台设备可能在不同网络，且微信回调不参与粘滞。
3. **鉴权查库频率**。握手时查一次 token/设备归属没问题；**绝不要在心跳里查库**——那是 333 QPS 的无谓数据库压力。

**连接数到底由什么决定**：连接数 = **已登录云端的设备数**（安装版按机器算、便携版按 U 盘算）。

⚠️ **不要把"便携版"当成减少连接数的因素**——便携版**同样要登录云端**（§7.1 / §7.5），它正常占一条连接。
真正带来折扣的是**物理约束**：一个 U 盘同一时刻只能插一台电脑
⇒ 无论它先后插过多少台教室电脑，**同一时刻只有一条连接**。

## 13. 安全清单

| 风险 | 措施 |
|---|---|
| 任何人往大屏推内容 | **只接受已绑定 openid**；未绑定回执引导配对 |
| 配对码被枚举 | 6 位 + 5min TTL + 一次性 + 每码 5 次失败作废 + openid 级限流 |
| 消息轰炸 / 微信被盗 | 每 openid 60s 内最多 5 条；超限回执 |
| XSS 打进 Electron 渲染进程 | 投屏页用 `textContent`，**绝不 `innerHTML`**；窗口 `contextIsolation:true` / `nodeIntegration:false` |
| 伪造回调 | 微信签名（SHA1 排序 token/timestamp/nonce）+ 强制 HTTPS |
| 公网扫描 | 回调路径可加**微信服务器 IP 段白名单**（本项目只需微信一方能连） |
| 越权推送 | WS 握手校验云端 token，只允许推给 token 对应的 `teacherId`；`deviceId` 必须属于该账号 |

**在 Electron 里 XSS 的后果比浏览器严重得多**，所以投屏页必须当作"不可信内容渲染"来写。

## 14. 实施分期

| 阶段 | 内容 | 关键点 |
|---|---|---|
| **P0** | 投屏窗口（全屏 + 气泡）+ SAPI 播报 + 本机配置 + `notify:test` | **不碰微信**，先把"看得见听得见"做扎实 |
| **P1** | 云端回调（验签/解析/幂等/被动回复）+ 指令语法 | 用**测试号** + cpolar 联调真实消息 |
| **P2** | 配对码绑定 + 出站 WS + 单设备投屏闭环 | **schema 从一开始就按多设备设计**（`deviceId` 单层 + `device`/`delivery` 扇出），即使只有一台 |
| **P3** | 多设备：设备管理页 + **定向投屏 `#通知 #3班 #…`** + 扇出投递 + 离线补推与过期 | 见 §7.1 / §7.2 / §7.3。**定向是核心能力，不延后** |
| **P4** | 正式公众号服务器配置 + Nginx + 域名备案 + 证书 | 合规与部署 |
| **P5** | 通知历史页、免打扰预设、`#全部` 批量播报 | 产品打磨 |

**P1 的顺序不能反**：在公众号后台点「提交」的瞬间，微信会**立刻发一个 GET 请求**做签名校验并要你原样返回 `echostr`。接口不响应，配置就存不下来 ⇒ **先写接口 → 再开穿透 → 最后配公众号**。

## 15. 订阅号的体验短板（提前知道）

- **订阅号被折叠**：老师在微信里要先点开「订阅号消息」再找到这个号，比服务号（在会话列表首层）多两步。引导老师把公众号**置顶/设为星标**能缓解。
- **不能主动推送**：投屏失败、定时提醒这类"云端主动告知"做不了（需认证）。所以设计上**回执只能靠被动回复 + `#状态` 查询**。
- **升级路径**：若将来升级为**认证服务号**（300 元/年，需企业/组织主体），可解锁：微信授权一键绑定、扫码绑定、主动推送回执。**但这些是体验优化，不是功能必需**——本设计的核心链路在订阅号上完整可用。
