# 班级积分系统设计方案

> 目标：以**班级为积分主体**，通过集体性游戏与集体常规，培养学生的集体主义精神。
> 适用范围：EduPlay 本地端（老师端 + 教室大屏）。管理后台（云端）不参与教学数据。
> 状态：设计方案（含落地计划），尚未实施。

---

## 0. 结论先行（核心决策）

| 决策点 | 结论 | 理由 |
|---|---|---|
| 班级积分从哪来 | **独立账户独立记账**，不是"学生积分之和" | 求和等于个人英雄主义 + 搭便车，尖子生拉高全班分，落后者无感 |
| 与个人积分的关系 | **双层并存、互不换算** | 个人分（现有 13 表）零改动，无回归风险 |
| 积分归属 | 班级整体，参与者是"全班" | 集体主义的核心是"我们" |
| 扣分策略 | **克制使用**，游戏失败默认 0 扣分 | 游戏变惩罚会摧毁参与意愿 |
| 结算周期 | 周榜为主 + 日榜 + 学期总榜，**周期结算不清零总分** | 清零会让落后班放弃，滚动累计 + 阶段勋章维持长期动机 |
| 大屏刷新 | **轮询**（2~3s），不用 WebSocket | 与项目现状一致（云端代理不能转发 WS），局域网轮询简单可验证 |
| 呈现形式 | 成长视觉（树/熊猫）+ 档位进度，裸数字为辅 | 初中生对"看得见的长大"响应远强于分数 |

## 1. 整体架构

### 1.1 双层积分模型

```text
┌──────────────────────────────────────────────────────────────┐
│  L1 个人积分（现有，不改动）                                   │
│  student.total_points  ──►  student_points_ledger            │
│  来源：个人游戏得分（GAME_COMPLETE）、教师手动调整              │
└──────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────┐
│  L2 班级积分（新增）                                           │
│  class_points_account  ──►  class_points_ledger              │
│  来源：集体游戏达标（GAME_CLASS_COMPLETE）、集体常规记录、连续达标加成 │
└──────────────────────────────────────────────────────────────┘
                    ▲
                    │ 可选展示（不是分配依据）
        「班级贡献榜」= 汇聚 L1 中本班学生的游戏分，仅作荣誉激励
```

**为什么不做"班级分 = 学生分求和"**（重要）：
求和模型下，班级分完全由少数高分学生决定。对集体主义而言它是**反向激励**——低分学生发现"我加不加分对班级没影响"，反而卸责；高分学生则成为唯一贡献者。真正培养集体认同，必须让班级分来自**只有全班一起才能达成的目标**（同步共振型游戏）或**明确"为班级而战"的分组对抗**。

### 1.2 数据模型（Flyway V15）

```sql
-- V15__class_points.sql

-- 班级积分账户：一个教师的一个班级一行
create table class_points_account (
    id            bigint generated by default as identity primary key,
    teacher_id    bigint       not null,
    class_name    varchar(64)  not null,
    total_points  int          not null default 0,   -- 学期总积分（跨周期累计，不清零）
    season_points int          not null default 0,   -- 当前结算周期积分（窗口值）
    level         int          not null default 0,   -- 成长档位 0..8
    season_key    varchar(16)  not null,             -- 当前周期，如 2026-W42
    version       bigint       not null default 0,
    created_at    timestamp    not null,
    updated_at    timestamp    not null,
    constraint fk_class_points_teacher foreign key (teacher_id) references app_user(id),
    constraint uk_class_points unique (teacher_id, class_name)
);

-- 班级积分流水：所有加减分唯一入口，可对账可追溯
create table class_points_ledger (
    id              bigint generated by default as identity primary key,
    account_id      bigint       not null,
    teacher_id      bigint       not null,
    class_name      varchar(64)  not null,
    change_type     varchar(32)  not null,  -- CLASS_GAME_EARN / CLASS_GAME_DEDUCT
                                            -- CLASS_ROUTINE_EARN / CLASS_ROUTINE_DEDUCT
                                            -- CLASS_STREAK_BONUS / CLASS_SEASON_SETTLE
    amount          int          not null,
    balance_after   int          not null,
    biz_type        varchar(32)  not null,  -- GAME_SCORE / ROUTINE / STREAK_BONUS / SEASON_SETTLE
    biz_id          varchar(64)  not null,
    game_code       varchar(64),
    season_key      varchar(16)  not null,
    evidence        varchar(512),           -- 判定证据摘要，可审计
    idempotency_key varchar(64)  not null unique,
    created_at      timestamp    not null,
    constraint fk_class_ledger_account foreign key (account_id) references class_points_account(id)
);

create index idx_class_ledger_account on class_points_ledger(account_id, created_at desc);
create index idx_class_ledger_season  on class_points_ledger(teacher_id, class_name, season_key);
```

**两个字段值得单独说明**：

- `evidence`：存游戏的判定证据摘要，例如 `quiet=62s avg=38dB ratio=0.92 stages=4`。
  麦克风类游戏的数据服务端无法验真，把证据落库后，任何一次加分都能被复述和复核——
  这是"数据可审计"在积分系统里的落点，也方便处理学生质疑。
- `total_points` 与 `season_points` 双计数器：周期结算时只切 `season_points` 窗口，
  总分不动。避免"清零打击"。

### 1.3 游戏协议扩展（向后兼容）

现有 13 个游戏的 manifest 均无新字段 ⇒ 缺省按 `scoreMode="student"` 处理，**零改动**。

manifest 新增可选字段：

```json
{
  "gameCode": "quiet_forest",
  "name": "小树木快长大",
  "version": "0.1.0",
  "type": "iframe",
  "requiresRoster": false,
  "scoreMode": "class",
  "coopType": "synchronized",
  "classSelMode": "pick",
  "classScoreCap": 30,
  "minDurationSeconds": 60,
  "entry": "web/index.html",
  "backendPlugin": null
}
```

| 字段 | 取值 | 含义 |
|---|---|---|
| `scoreMode` | `student`(默认) / `class` / `hybrid` | 积分记到哪本账 |
| `coopType` | `synchronized` / `relay` / `versus` / `display` | 集体参与形态，决定 UI 呈现 |
| `classSelMode` | `pick` / `all` | 启动器是否必须选一个班 |
| `classScoreCap` | int | 单次班级加分上限（平台兜底，防游戏端写大数） |
| `minDurationSeconds` | int | 最短有效时长，服务端校验，拒绝"秒刷" |

新增游戏 → 平台消息：

```json
{
  "source": "eduplay-game",
  "type": "GAME_CLASS_COMPLETE",
  "payload": {
    "roundId": "f3a1...uuid",
    "className": "初二3班",
    "classScore": 20,
    "metrics": {
      "durationSeconds": 62,
      "avgDb": 38,
      "quietRatio": 0.92,
      "stages": 4,
      "maxDb": 71
    }
  }
}
```

新增接口：

```text
POST /api/v1/games/{gameCode}/class-scores
Authorization: Bearer {token}

{ "className": "初二3班", "score": 20, "roundId": "f3a1...", "metrics": { ... } }
```

响应：

```json
{
  "success": true, "code": "OK",
  "data": {
    "className": "初二3班",
    "totalPoints": 245, "seasonPoints": 85,
    "level": 3, "levelName": "小树",
    "delta": 20, "recorded": true,
    "evidence": "quiet=62s avg=38dB ratio=0.92 stages=4"
  }
}
```

**服务端五道防刷护栏**（游戏端算分、服务端必须独立限流）：

1. 幂等：`idempotencyKey = sha256(gameCode : className : roundId)`，重复提交直接返回原结果；
2. 时长：`metrics.durationSeconds ≥ minDurationSeconds`，否则 `INVALID_DURATION`；
3. 单次上限：`score ≤ classScoreCap`；
4. 单日频率：同班 + 同游戏，每天最多计分 3 次；
5. 单周期总额：同班 + 同游戏，单周期累计最多 100 分。

## 2. 积分规则

### 2.1 加分来源

| 来源 | 触发方式 | 分值 | 频次上限 |
|---|---|---|---|
| 合作游戏达标 | 游戏判定后自动提交 | +10 ~ +30（分档） | 见 §2.4 |
| 全员到齐 / 全勤 | 教师一键记录 | +5 | 每日 1 次 |
| 集体作业全交 | 教师一键记录 | +5 | 每日 1 次 |
| 课堂纪律 / 卫生达标 | 教师一键记录 | +3 | 每日 1 次 |
| 集体互助（同学间互相帮助） | 教师记录 + 文字描述 | +5 | 每周 +15 上限 |
| 连续达标加成 | 系统自动结算 | +10 / +20 / +50 | 连续 3 / 5 / 10 天 |
| 班级展演 / 被评优 | 教师确认 | +10 | 无（人工把关） |

协作类加分全部走"贴标签"式一键操作（无需输入分值），降低教师负担——这是能否长期用下去的关键。

### 2.2 扣分机制（克制原则）

**第一条原则：游戏失败不扣分。** 游戏如果会扣分，学生就会回避游戏、互相指责，
集体主义反而被破坏。未达标显示"再试一次"即可。

扣分只用于**集体性、可复述的具体失误**，且必须填理由（写入 `evidence`）：

| 场景 | 分值 | 例 |
|---|---|---|
| 集体常规失误 | -3 | 全班作业未交齐、卫生未打扫 |
| 严重集体违纪 | -5 ~ -10 | 需要教师描述具体情况 |

**三条护栏**：

1. 单日扣分总额 ≤ 9 分（防止情绪化连扣）；
2. 账户余额下限 0（不允许负分，负分让落后班彻底摆烂）；
3. 扣分与加分走同一账本、同一幂等机制，全部可追溯。

### 2.3 上限与档位

| 对象 | 上限 |
|---|---|
| 单次游戏 | ≤ `classScoreCap`（默认 20，上限 30） |
| 单日班级总分增长 | ≤ 60 |
| 单周期 + 单游戏 | ≤ 100 |
| 学期总分 | 无硬上限 |

**成长档位**（视觉封顶，分数继续累计）：

| 档位 | 名称 | 累计积分阈值 |
|---|---|---|
| 0 | 种子 | 0 |
| 1 | 破土 | 30 |
| 2 | 幼苗 | 80 |
| 3 | 小树 | 150 |
| 4 | 成树 | 250 |
| 5 | 含苞 | 380 |
| 6 | 开花 | 550 |
| 7 | 结果 | 780 |
| 8 | 森林 | 1100+ |

档位封顶后视觉不再变化（避免审美疲劳），但学期总分继续排名——**短期看成长，长期看排名**。

### 2.4 结算周期

| 周期 | 长度 | 结算动作 | 产出 |
|---|---|---|---|
| 日榜 | 当日 | 0:00 切窗口 | 当天积分排名 |
| 周榜（默认） | ISO 周 | 周一 00:00 结算上周 | 周冠军班、进步最快班、周勋章 |
| 学期总榜 | 学期 | 期末封榜 | 班级勋章、学期称号 |

- `season_key` 采用 `2026-W42`（ISO 周）/ `2026-FALL`（学期）格式；
- 结算写一条 `CLASS_SEASON_SETTLE` 流水记录周期归档结果，**不改动** `total_points`；
- 周结算用 Spring `@Scheduled`（本地端已有后端进程，无需外部调度）。

## 3. 游戏分类设计

四个类别按"集体参与形态"划分。**A 类才是集体主义的核心载体**——
只有"全班共同达成、任何人破坏就失败"的机制，才能真正培养"我在集体中的责任"。

| 类别 | 名称 | 参与形态 | 积分对象 | 与积分关联方式 |
|---|---|---|---|---|
| **A** | 同步共振型 | 全班同时做同一件事，共同达成阈值 | 班级 | 达标即加分，按"维持时长 / 达标率"分档 |
| **B** | 接力累积型 | 每人完成一段，分数累加为班级分 | 班级 + 个人 | `hybrid`：个人分段分 + 班级汇总加成 |
| **C** | 分组对抗型 | 班内分组 PK，荣誉归全班 | 班级 | 胜方加分，负方不扣，平局双方小加分 |
| **D** | 展示沉浸型 | 无输赢，纯教学展示 / 观察 | 无 | 不积分，记录"使用课时"用于学期活跃度 |

**现有 13 个游戏映射**：

| 游戏 | 类别 | 说明 |
|---|---|---|
| 气象要素识别 `weather_quiz` | A | 全班同时作答，以班级平均正确率判定 |
| 行政区拼图 `province_puzzle` | B | 每人拼一段，累加为班级进度 |
| 省级行政区识别 `province_quiz` | B | 同上 |
| 地图图例消消乐 `legend_match` | B | 同上 |
| 经纬度五子棋 `geo_gomoku` | C | 分组对弈，胜方为班级挣分 |
| 捕鱼达人·洋流版 `fish_master` | C | 分组对抗 |
| 山河三消 `shanhe_match3` | C | 分组对抗（也可做 B 类接力） |
| 寰宇地球仪 `earth_globe` | D | 展示 |
| 寰宇月球 `moon_globe` | D | 展示 |
| 寰宇太阳系 `solar_system` | D | 展示 |
| 山河塑形·中国地形 `china_relief` | D | 展示 |
| 口袋地形 `mountain_zones` | D | 展示 |
| 地貌人格测试 `landform_quiz` | D | 展示 / 趣味 |

新增（本方案配套）：**小树木快长大 `quiet_forest`** — A 类，见 §4。

**关联实现**：`manifest.scoreMode` 决定走哪本账；`manifest.coopType` 决定 UI 呈现
（A 类显示"班级合力条"，B 类显示"接力进度 + 班级总分"，C 类显示"分组比分板"，D 类不显示积分区）。
游戏本体不需要知道积分规则，只负责产生 `metrics` 与 `classScore`。

## 4. 机制示例：小树木快长大 `quiet_forest`

### 4.1 玩法

教师在教室里打开游戏 → 全班一起"安静陪小树长大"。
麦克风采集环境分贝，**分贝越小，小树成长越快**；满足时长条件后为班级加分。

### 4.2 判定链路

```text
① 教师端启动器：只选班级（scoreMode=class ⇒ 不选学生）
② 游戏请求麦克风 getUserMedia({audio:true})
③ AnalyserNode 每 100ms 取 RMS → dBFS → 归一化安静度
      quiet = clamp((thresholdDb - measuredDb) / (thresholdDb - floorDb), 0, 1)
      thresholdDb = 55（超过即"吵"）, floorDb = 30（低于即"满分安静"）
④ 成长累加：
      growth += quiet * k          （k = 10 成长点/秒）
      若 quiet < 0.3 持续 3s ⇒ 停滞（growth 不增长，也不回落）
⑤ 阶段推进：
      stage = floor(growth / stageCost)     （stageCost = 60 ⇒ 满分安静约 6s 长一阶段）
⑥ 结束判定：
      durationSeconds ≥ minDurationSeconds (60s)  且  stage ≥ 3  ⇒ 达标
      classScore = 10 + (stage - 3) * 5，封顶 classScoreCap (30)
⑦ 发送 GAME_CLASS_COMPLETE（带 metrics）→ 平台调 /class-scores 落账
```

### 4.3 分档表

| 阶段数 | 画面 | 判定 | 班级得分 |
|---|---|---|---|
| < 3 | 树苗 | 未达标 | 0（显示"再来一次"，**不扣分**） |
| 3 | 小树长成 | 达标 | +10 |
| 4 | 枝叶茂盛 | 良好 | +15 |
| 5 | 开花 | 优秀 | +20 |
| ≥ 6 | 结果 / 森林 | 卓越 | +25 ~ +30 |

### 4.4 为什么用"归一化安静度"而不是绝对 dB

绝对分贝需要专业校准，教室设备差异大（笔记本内置麦 vs 外接麦 vs 一体机）。
方案给一个**基线标定页**：教师点"采集教室静音基线 3 秒"，把当时的电平记为 `floorDb`，
再取一个"吵闹参考"记为 `thresholdDb`。之后全部用相对值判定，跨设备可用。

**兜底**：若麦克风不可用（无权限 / 无设备），切换"手动模式"——
由教师按"安静 / 一般 / 吵"三档点按，游戏按等效成长速度推进。保证任何教室都能用。

### 4.5 反作弊与公平性

| 手段 | 说明 |
|---|---|
| 幂等 `roundId` | 同一局重复提交不重复加分 |
| 服务端时长校验 | `durationSeconds ≥ 60`，拒绝"秒刷高分" |
| 单次 / 单日 / 单周期上限 | 见 §1.3 五道护栏 |
| 教师端实时波形 | 教师能看见真实音量条，人为作假当场可见 |
| 教师"判无效"按钮 | 发 `GAME_ERROR` / abort，本局不结算 |
| `evidence` 落库 | 每笔加分可复核，学生有异议可查 |

麦克风数据本质上无法服务端验真，因此**所有权衡落在"教师在场 + 证据留痕"**，
而不是试图做技术性防伪——这也是成本最低、最符合课堂实际的方案。

### 5.2 教室大屏是重点（增强集体荣誉感的主战场）

大屏的价值在于**"路过就能看懂"**：一个主视觉 + 一个主数字 + 一条事件流。

- **主视觉**：会随积分长大的树（或 IP 熊猫抱西瓜的养成形态），每升一档明显变化；
- **主数字**：班级总分（滚动动画）、本周期分、档位名、距下一档进度环；
- **实时条**：游戏进行时显示"此刻安静度"波形与成长条；
- **事件流**：最近加分事件滚动播报（"全员到齐 +5"、"和小树一起长大 +20"）；
- **周期榜**：本班在年级 / 全校的排名条（用相对位置，弱化绝对名次）。

**数据刷新**：轮询 `GET /api/v1/classes/{className}/points` 每 2~3 秒。
不用 WebSocket —— 本地端 `CloudApiProxyController` 带 `@Profile("local")` 且基于
`HttpURLConnection`，**无法转发 WebSocket**；轮询在局域网内足够且简单可验证。

**投屏方式**：教师端 GamePage 提供「投到大屏」按钮 → `window.open` 打开大屏页（独立窗口），
教师端继续可操作，互不阻塞。

### 5.3 呈现形式原则

1. **数字可感知**：用成长视觉 + 进度条替代裸分数，符合初中生认知；
2. **荣誉归集体**：用称号 / 勋章（周冠军、进步之星、安静之班）呈现，弱化个人排名；
3. **双色区分**：班级积分用金色 / 绿色系，个人积分保持现有蓝色系，避免混淆；
4. **少即是多**：大屏只保留"一个主视觉 + 一个主数字 + 一条事件流"，不堆表格。

### 风险与对策

| 风险 | 对策 |
|---|---|
| 教室麦克风设备差异大 | 基线标定页 + 归一化安静度；提供手动模式兜底 |
| 大屏占用投影导致教师无法操作 | 大屏独立窗口，教师端不受影响 |
| 班级分与个人分混淆 | UI 双色区分 + 文案明确"这是班级的分" |
| 教师记录负担过重（导致弃用） | 一键贴标签式记录，不输入分值 |
| 扣分引发对抗情绪 | 游戏失败零扣分 + 单日扣分上限 + 余额下限 0 |
